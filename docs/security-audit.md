## Детальное описание

### 1. Захват чужих каналов (CRITICAL)

**Описание:** Функция `_try_add_channel` проверяет, что **бот** является админом канала, но **не проверяет**, является ли **пользователь** администратором этого канала.

**Эксплуатация:**
1. Пользователь A владеет каналом `@my_channel` и добавил бота администратором
2. Злоумышленник B пересылает любое публичное сообщение из `@my_channel` боту
3. Бот проверяет: «Я админ? Да» — и добавляет канал в аккаунт B
4. Теперь B может публиковать произвольные посты в канал A

Альтернативный вектор — отправка `@my_channel` как текста.

**Воздействие:** Полный контроль над контентом чужого канала. Публикация спама, фишинга, деструктивных сообщений.

**Рекомендация:** Добавить проверку `bot.get_chat_member(channel_id, message.from_user.id)` — пользователь должен быть администратором или создателем канала.

---

### 2. HTML-инъекция через название канала (HIGH)

**Описание:** Бот использует `ParseMode.HTML`. Названия каналов подставляются в сообщения без экранирования.

**Эксплуатация:**
1. Злоумышленник создаёт канал с названием `Мой <a href="https://phishing.com">канал</a>`
2. Добавляет бота админом и регистрирует канал
3. Название подставляется в HTML-сообщения как есть → фишинговая ссылка внутри интерфейса бота

Если название содержит невалидный HTML (`<`, `>` без тегов) — Telegram API вернёт ошибку, обработчик упадёт (мини-DoS).

**Затронутые места:**
- `posts.py:381` — `f"✅ Пост опубликован в «{title}»!"`
- `posts.py:603` — аналогичное при republish
- `channels.py:128` — `f"✅ Канал «{title}» успешно добавлен!"`

**Рекомендация:** Использовать `html.escape()` для всех пользовательских строк в HTML-сообщениях.

---

### 3. Раскрытие информации через сырые исключения (HIGH)

**Описание:** При ошибке публикации полный текст Python-исключения отправляется пользователю.

**Затронутые места:**
- `posts.py:369–375` — publish
- `posts.py:592–598` — republish

**Утечка:** Внутренний `channel_id`, детали Telegram API ошибок, потенциально — версии библиотек, внутренние адреса.

**Рекомендация:** Показывать пользователю общее сообщение, детали писать в лог с `exc_info=True`.

---

### 4. Отсутствие валидации callback_data (MEDIUM)

**Описание:** Значения из `callback.data.split(":")[N]` приводятся к `int()` без `try/except`. Пользователь может отправить произвольный callback через API.

**Затронутые места (int() без защиты):**
- `posts.py:347, 482, 497, 536, 549, 572–573`
- `channels.py:152`

**Эксплуатация:** Отправка `callback_data = "post_v:abc"` → `ValueError` → необработанное исключение → callback не отвечен (вечная загрузка у пользователя).

**Рекомендация:** Обернуть в `try/except (ValueError, IndexError)` или создать утилитарную функцию парсинга.

---

### 5. Отсутствие rate limiting и лимитов на ресурсы (MEDIUM)

**Описание:** Нет ограничений на:
- Частоту запросов от одного пользователя
- Количество каналов на пользователя
- Количество постов на пользователя
- Количество кнопок в посте

**Эксплуатация:** Скрипт создаёт тысячи постов → рост БД → исчерпание диска. Массовые публикации → Telegram rate limit 429 → бот заблокирован для всех.

**Рекомендация:**
- Throttling middleware (простой TTLCache или aiogram throttling)
- Лимиты: ~50 каналов, ~500 постов, ~25 кнопок (5 рядов по 5)

---

### 6. Единое DB-соединение (race conditions) (MEDIUM)

**Описание:** Один `aiosqlite.Connection` на все обработчики. `commit()` одного обработчика фиксирует незавершённые операции другого.

**Пример:** Обработчик A делает INSERT, обработчик B делает DELETE + commit → commit B фиксирует и INSERT A до завершения логики A.

**Рекомендация:** Создавать отдельное соединение на каждый update в middleware:
```python
async with aiosqlite.connect(self._db_path) as conn:
    data["db"] = conn
    return await handler(event, data)
```

---

### 7. Forward-сообщения вне FSM-контекста (MEDIUM)

**Описание:** Обработчик `handle_forwarded_from_channel` не защищён FSM-состоянием. Если пользователь в процессе создания поста пересылает сообщение из канала — вместо сохранения текста бот пытается добавить канал.

**Рекомендация:** Либо проверять отсутствие FSM-состояния (`~StateFilter("*")`), либо ввести явное состояние `AddChannel.waiting_for_forward`.

---

### 8. Перехват `@username` сообщений (MEDIUM)

**Описание:** Фильтр `F.text.startswith("@")` ловит любое сообщение с `@` в начале. Пользователь может случайно попасть в flow добавления канала, отправив `@mention`.

**Также:** бот раскрывает существование канала и статус бота в нём (information disclosure).

**Рекомендация:** Строгий regex: `F.text.regexp(r"^@[a-zA-Z][a-zA-Z0-9_]{3,31}$")` и/или привязка к FSM-состоянию.

---

### 9. Отрицательные значения пагинации (LOW)

**Описание:** `posts_pg:-10` → `offset = -50` → SQLite трактует как 0, но в интерфейсе показывается `-9/N`.

**Рекомендация:** `page = max(0, int(...))`.

---

### 10. MemoryStorage для FSM (LOW)

**Описание:** FSM-состояния хранятся в памяти. При рестарте бота все пользователи теряют текущее состояние, посты в процессе создания могут остаться «бесхозными» в БД.

**Рекомендация:** Для MVP допустимо. В будущем — Redis или файловое хранилище.

---

## Что НЕ является уязвимостью

- **SQL-инъекция:** Все запросы используют параметризованные плейсхолдеры `?`. Невозможна.
- **Межпользовательский доступ к данным:** Все критические SQL-запросы проверяют `user_id`. Пользователь A не может удалить/просмотреть/опубликовать посты пользователя B.
